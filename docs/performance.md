# 性能与基准测试

[返回 README](../README.md)

日记、用量、快照的 IndexedDB 读写，以及日记压缩和摘要，都跑在 [日记工作线程](../src/client/worker/journal.worker.ts) 里。高度网格和岛的顶点跑在 [世界工作线程](../src/client/worker/world.worker.ts) 里。这些任务交给工作线程后，主线程继续处理模拟、场景更新和渲染。没有 module Worker 的环境在主线程做同样的事，行为不变。

运行全部基准测试。

```bash
pnpm bench
```

`pnpm bench` 会输出各条路径的耗时和每秒次数，覆盖岛屿创建，空转和驱动各 120 帧，绕开巢寻路，快照的捕获和恢复，世界线程烘焙以及网格和 `islandBuffers` 的拆分，主线程装扮拆成巢、苹果和草，还有 400 轮日记的估算、装入、丢弃和誊写。这些数字不会让构建失败。`pnpm test` 里的 `tests/perf/budget.test.ts` 给这些路径设了宽松的毫秒上限，这些预算仅在本地运行，GitHub CI 会排除这组依赖机器耗时的测试。测试范围包括空转和驱动各 120 帧、绕开巢寻路、世界线程烘焙岛屿、主线程装扮岛屿，以及已有的快照和日记。这些上限用于发现数量级的性能退化，例如算法复杂度意外变成平方级；百分之几的波动不属于预算测试的判断范围。浏览器绘制、网络和模型不在这些预算里。

场景性能可单独运行。

```bash
pnpm exec vitest bench benchmarks/scenery.bench.ts --run --reporter=verbose
```

这组基准覆盖整座岛上的树、石、沼石、巢和草的模型创建，草的贴地，以及每轮几何释放；地表拆成纯地面烘焙、带短草苔藓的完整烘焙和主线程组装。运行路径包括 120 次草丛遮挡查询、带真实场景障碍且已确认可达的绕行，以及当前存档、无景物旧存档、密集草版本的恢复。恢复基准复用已烘焙地形，原有 `apply a body` 基准则包含地形重建。初始化和路线选择在计时外完成。

耗时列中的 mean、p75、p99 等数值单位为毫秒，hz 表示每秒次数。模型创建是启动时的一次性开销，不能当成每帧耗时；Node 基准也不包含 GPU 上传、阴影、浏览器绘制和相机移动，需要浏览器性能录制补充判断。Vitest 如提示 module export getter 开销，跨版本比较时应使用相同运行方式。

持续运行的热点另有 `benchmarks/runtime.bench.ts`，拆分 120 帧天空动画、移动蜘蛛时的苹果物理和 120 次墙体探测。可与驱动帧一起运行。

```bash
pnpm exec vitest bench benchmarks/runtime.bench.ts benchmarks/frame.bench.ts --run --reporter=verbose
```

`reset whole world` 场景在每次采样前恢复完整快照，恢复本身不计时，避免苹果在重复采样中逐渐静止而让结果偏低。云采用每朵独立的实例批次，保留云间透明排序和剔除；批次数量测试不能替代浏览器 GPU 帧时间测量。

## 浏览器本机推理性能

本机推理和 Three.js 场景可能共用 GPU。Worker 隔离 JavaScript/WASM 工作，不隔离 GPU 资源。

### 当前策略

- 使用一个 WebLLM 引擎。交互优先于日记摘要；交互到来时，中断摘要并在交互结束后重试。工具执行期间保留交互会话，避免日记提示词打断 KV cache。
- 每次交互保留模型原始 assistant 回复，包括空白和 reasoning 标记。传给 SDK 的工具 JSON 仅用于解析；下一轮恢复原始消息，满足 WebLLM 的会话匹配条件。匹配失败时正常重新 prefill，不拼接不相关历史。
- 本机工具提示词省略 Schema 注释，保留参数类型、必填项和校验约束；行动输出上限为 256 token，日记为 384 token。截断回复不能执行工具。
- Worker 每约 40ms 合并一次增量，首个增量立即发送。普通回答使用内部 `答：` 前缀区分，前缀不显示；未标记回答等待完成后分类。工具消息等待完整解析与 SDK 参数校验；未知工具数据显示错误，不进入气泡。
- 仅在加载模型和实际推理期间，绘制 DPR 上限为 1、绘制频率上限约 30 FPS；模拟仍按原动画回调推进。模型返回后立即恢复 DPR 上限 2 与原绘制频率，蜘蛛执行工具动作时保持正常清晰度。会话保留只控制摘要调度，不触发降画质。

### 观察指标

「用量」中的本机任务请求详情记录排队时间、模型首 token、生成耗时、prefill/decode token/s。界面的「首字响应」包含 SDK 消息分类等开销，与模型首 token 含义不同。WebLLM 的 prompt token 可能只计算新增 prefill 部分，不能把它直接视为完整上下文长度或据此推算准确缓存命中率。

悬停 FPS 可查看最近半秒绘制帧间隔 P95/P99 和超过 50ms 的长帧数量。它衡量帧间隔，不是 GPU 内核执行时间；分析主线程长任务仍需浏览器 Performance 面板。

### 真机对比流程

1. 使用正式构建与 `pnpm preview`。固定浏览器版本、供电状态、场景、视口和 DPR，记录 GPU 信息。
2. 将首次下载、已有下载缓存的加载、模型已就绪的热运行分开。记录第一次运行，另做一次预热后再测热运行。
3. 固定指令「看看周围」「右转九十度」「走到一个可见目标旁边」，每项重复至少 20 次，记录成功率、模型调用次数、首次动作与完成时间。
4. 对比修改前与修改后；诊断时另做正常画质、当前低负载画质、仅暂停绘制但保留模拟三组。不要用冻结模拟代替暂停绘制，否则工具完成时间不可比较。
5. 同时比较请求耗时 P50/P95、帧间隔 P95/P99、长帧数量和任务成功率。不要仅比较 token/s。
6. 摘要生成时发起新指令，以及生成过程中取消、换指令、释放模型，确认无错误行动、任务挂起或画质不恢复。

这里的自动化测试验证消息、调度、流式和模拟行为，不包含真实 GPU 性能结论。实际收益以同设备对照为准。

应用侧消息处理可单独测量：

```bash
pnpm exec vitest bench benchmarks/local.bench.ts --run --reporter=verbose
```

这组基准使用真实三个工具的 Schema，测量提示词压缩、嵌套工具消息解析、4 KiB 未闭合 JSON 的扫描，以及每片 8 字符的工具消息流分类，不加载模型或使用 GPU。本地一次对照中，工具 Schema 从 3102 B 减至 1513 B（51.2%）；未闭合 JSON 扫描从约 15.6ms 降至 0.0076ms，修复了重复扫描嵌套括号的问题。普通嵌套消息解析约 0.001ms，流分类约 0.0055ms。这些数字是当前机器的 Node 测量，不能解释为 GPU 推理提速倍数。

`tests/perf/budget.test.ts` 另检查连续处理 25 条此类异常消息在 25ms 内完成，防止平方级扫描回归；与其他依赖机器的预算一样，仅在本地运行。

### 后续编译实验

当前模型库为固定版本的 `cs1k` WASM。WebLLM 0.2.87 从 WASM 编译元数据读取 `prefill_chunk_size`，仅修改运行时 `overrides` 不会改变分块。只有在基准表明 prefill 长帧占主要部分后，再制作 256/512 分块的兼容构建，比较首 token、长帧、吞吐和显存；分块越小不一定越快。
